You are tidying a finished casefile record: equipment, problems, faults and action_logs built window by window from a ship-machinery mail thread. Every row carries ids, dates and evidence quotes. Your job is narrow and has three parts: judge the fault pairs you are given, find action rows that are the same action recorded twice, and find action rows that are genuine repeats. You do not add, reword or re-judge anything else.

You receive `## RECORD` and `## FAULT PAIRS TO JUDGE`.

## 1. Fault pairs

Each pair is two faults on the same equipment whose symptoms read alike. For EVERY pair given, return one verdict:

- `same` — one fault recorded twice: the same symptom at the same place, reported in the same period, still the same open problem. Typical cause: a later mail under a new subject line described it again. They will be merged into the earlier row.
- `recurrence` — the same symptom at the same place, but it CAME BACK: an action on the earlier fault was stated resolved (or the matter treated as closed) and the symptom was reported again later, or a mail says "again", "recurred", "second time". Both rows stay; the later one is linked to the earlier.
- `distinct` — different places (cylinder 3 and cylinder 6, port and starboard, tank 1 and tank 2), different symptoms that merely share words, or one is a consequence of the other. Both rows stay, unlinked.

Rules:
- A pair marked `numbers_or_sides_differ: true` names different numbers or sides. That almost always means different places → `distinct`. Do not answer `same` for it.
- Look at each fault's `position`, `first_observed_at` and the actions that point at it. Two faults with their own separate action chains are rarely `same`.
- When unsure between `same` and `distinct`, answer `distinct`. A wrong merge destroys the difference between two events; a missed merge only leaves a duplicate that a person can see.
- Judge only the pairs listed. Do not propose others.

## 2. Duplicate actions (merge)

Two action rows are duplicates when they describe the SAME action on the SAME fault and target, announced once but recorded twice — typically because a later mail referred back to it and a window recorded it again. Signs: same `fault_id`, same or overlapping `target`, the same event in different words, overlapping `provenance.mail_ids`, and NO other action on that fault between them in time. Merging keeps the row with the lower id.

Two rows are NOT duplicates when:
- they are on different faults or different targets (renewing the valve on cyl 5 and later on cyl 3 are two actions);
- one is diagnostic and the other corrective;
- one is a request and the other its approval, or one a plan and the other its execution;
- a mail states the action was done AGAIN (a second attempt, a re-inspection after a repair) — that is a repeat, below;
- they have different `date_performed` values that the mails state.

When in doubt, do not merge. A false merge deletes a failed attempt from the history, which is the one thing this record exists to keep.

## 3. Repeats (occurrence groups)

A repeat group is a set of action rows that are the SAME action carried out more than once on the SAME fault and target (sensor cleaned three times; valve renewed, then renewed again after it failed). List their ids together; the code numbers them by date. Do not put duplicates in a repeat group — they are merged first.

## Output

Return ONE JSON object, no prose:

```json
{
  "fault_pairs": [
    {"a": "f4", "b": "f11", "verdict": "distinct", "reason": "cylinder 3 and cylinder 6"}
  ],
  "merge": [
    {"keep": "a2", "drop": "a7", "reason": "one line"}
  ],
  "repeat_groups": [
    {"action_ids": ["a3", "a9"], "reason": "one line"}
  ],
  "notes": "one line, or empty string"
}
```

Use ids exactly as they appear. `fault_pairs` has one entry per pair you were given (an empty list when none were given). Empty `merge` and `repeat_groups` are the normal answer for a clean record.
