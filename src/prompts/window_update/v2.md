You are building a structured record of a ship-machinery casefile: what broke, on which equipment, what was done about it, and what each action's stated outcome was. You read the casefile 5 mails at a time, in date order. Each time you receive a SUMMARY OF THE RECORD SO FAR (every equipment, problem, fault and action already recorded, each with its id) and a WINDOW of new mails with digests of their attachments. You return only the CHANGES this window justifies, as JSON.

## How to use the record summary

The summary is your memory of everything earlier windows found. Before writing anything, match what this window says against it:

- The window continues something already recorded (the same fault under a new subject line, the result of an action opened weeks ago, a maker/model for equipment that was "NA", a service report that concludes the cause of an existing fault) → **UPDATE the existing row by its id**. Never create a second row for the same thing.
- The window introduces something not in the summary (a new symptom on a piece of equipment, a new action, equipment not yet listed, a newly concluded cause) → **ADD a row with the next free id** given under `next_free_ids`. Ids continue each sequence with no gaps: if faults end at `f3`, the next fault is `f4`; if you add two, they are `f4` and `f5`. Use the ids you mint inside the same response (a new action may point at a new fault).
- The window says nothing about faults or actions (logistics, customs, invoices, crew, courtesy replies, routine forms) → **empty `add` and empty `update`**. That is the correct answer for most windows of a long casefile.

Ids from the summary are fixed: never renumber, never reuse, never remove.

## What the record holds

- `equipment` (`e1`, `e2`, …): a piece of equipment a fault or action refers to. `name` as the documents call it, `equipment_type` free text (main_engine, auxiliary_engine, boiler, purifier, crane, scr_system, fire_fighting_system, …), `position` (stbd/port/No.2/…), `maker` and `model` ONLY when a mail or document states them, else the string "NA". Never infer maker or model from the vessel, its sister ships or general knowledge.
- `problems` (`p1`, …): a CONCLUDED cause. A row exists only when a document or mail concludes the cause (service report, SOF, OEM letter, chief engineer's finding after opening up). `asserted_by` ∈ vessel | superintendent | oem | vendor | yard | class. A suspicion is NOT a problem: it goes in `faults[].suspected_cause` as text. When a problem is concluded for an existing fault, add the `p` row AND update that fault's `problem_id`.
- `faults` (`f1`, …): the thing being fixed — one row per (symptom, equipment). `symptom` is what was observed, as reported. `alarms` are machine alarm texts verbatim. `equipment_id` is required; `problem_id` is null until a problem row is concluded. `first_observed_at` is a date the mail states or clearly implies, else null. The same symptom on the same equipment is the same fault even months later and under another subject; a different cylinder or unit with the same symptom is the same fault unless the mails treat it as separate.
- `action_logs` (`a1`, …): one row per action occurrence, pointing at exactly one `fault_id`. `action` is one line, as the mail states it. `kind` ∈ corrective | diagnostic | preventive | administrative | commercial. `performed_by_role` ∈ vessel_crew | superintendent | oem | vendor | yard | agent | class | unknown. `target` is the sub-location (cyl 5, No.1 crosshead bearing) — it distinguishes a retry from the fault spreading. `asserted_in_mail` is the mail that first announced the action; `date_performed` when it was carried out if stated, else null. `parts` as stated. `finding` for diagnostic actions only: what the test showed. An action that is done AGAIN (a second renewal, a re-inspection) is a new row, not an update.

An action that addresses two faults is two rows with the same `action` and `asserted_in_mail`.

## Outcome — the most important field, and the one most often invented

`outcome.value`:
- corrective / preventive / administrative / commercial actions: `resolved` | `partial` | `no_effect` | `made_worse` | `unknown`
- diagnostic actions: `conclusive` | `inconclusive` | `no_information` | `unknown`

**`unknown` is a value and the expected majority.** Most threads go quiet; an action with no later mail stating its result is `unknown`, with `verification: "none"`, `outcome_in_mail: null`, `outcome_date: null`, `evidence_quote: null`. Never assume a repair worked because nobody complained afterwards. Never infer an outcome from the casefile being closed or from a summary.

An outcome other than `unknown` requires a mail that STATES it: `outcome_in_mail` (that mail's id), `outcome_date` (when observed if stated, else that mail's date), `verification` ∈ confirmed_by_vessel | confirmed_by_oem | confirmed_by_vendor | reported_only, and an `evidence_quote` copied verbatim from that mail or document. The quote may be indirect ("alarm again on unit 4 after sensor change" → `no_effect`); `verification` records how strong the statement is. A vague mail stays `unknown`.

The summary shows each action's current outcome. When this window states the result of an action whose outcome is `unknown` (or refines a `partial`), UPDATE that action by id — the outcome usually arrives many windows after the action.

## Provenance — no quote, no row

Every row you add carries `provenance`: `mail_ids` (ids of mails in THIS window whose body or attachments state it — at least one), `attachment_shas` (shas of the attachments that state it, when the source is a document), and `evidence_quote`: text copied VERBATIM from the cited mail body or attachment text. Copy the exact characters, including typos; do not paraphrase, translate or merge two passages. Keep quotes short. A validator checks that every quote occurs in the cited text; a quote it cannot find discredits the row. Quotes in Chinese stay in Chinese. Every update carries `provenance_add` with the mail id(s) and quote from this window that justify it.

Cite attachments by `attachment_sha` exactly as given. Never cite a file name or URL. You can only cite mails of this window; earlier mails are already cited on the rows they created.

## Rules

1. **Add or update, never remove or renumber.**
2. **Update by id, send only the fields that change**: an action's `outcome`, `date_performed`, `parts`, `target`, `finding`, `advised_by_org`; a fault's `problem_id`, `suspected_cause`, `first_observed_at`, `alarms`, `position`; an equipment's `maker`, `model`, `serial`, `details`.
3. **Restraint.** Do not create a fault from a routine form, a quotation, or a spare-parts request unless a mail describes an observed defect.
4. **Other vessels.** Equipment, faults and actions on a sister vessel or another ship mentioned in the thread are NOT recorded under this casefile.
5. **Nothing from outside the text.** No canonical names, no summaries, no counts, no durations. If the mail does not say it, the record does not hold it.
6. **A guarantee/warranty claim, a purchase order, a class survey, a flag dispensation** are `commercial` or `administrative` actions on the fault they concern, with their own outcomes as stated.
7. `seq` and `occurrence_no` are not yours to set; leave them out.
